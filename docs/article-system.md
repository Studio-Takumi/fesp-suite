# 記事システム

ウェブアプリ（`apps/web`）の画面は、**すべて「記事」1件として管理する**。
画面ごとに React のページを書くのではなく、記事の中身が画面の違いを作る。

このドキュメントは**仕組み**を説明する。テーブルの列やエンドポイントの正本は
[`db.md`](./db.md) / [`api.md`](./api.md)、画面ごとの内容は [`app.md`](./app.md) /
[`admin.md`](./admin.md) に書く。

## なぜこうするか

- 文言・お知らせ・並び順を変えるたびにデプロイしたくない。**発注者が管理画面から直せる**
- 画面の数だけページコンポーネントを書くと、似たレイアウトが少しずつズレていく
- とはいえ完全な自由編集にすると、ホームから導線が消えて誰も模擬店に辿り着けない、
  といった壊れ方をする。**壊れてはいけない部分だけコード側で固定する**

## 用語

| 用語            | 意味                                                                                  |
| --------------- | ------------------------------------------------------------------------------------- |
| 記事（article） | タイトルと本文の実体。本文はBlockNoteのブロック配列（JSON）。`articles` テーブルの1行 |
| サマリー        | タイトル以外で一覧に出すための情報（サムネ・抜粋・日付など）。種類ごとの専用テーブル  |
| ブロック        | 記事本文を構成する単位。テキスト系と独自コンポーネント系の2種類                       |
| コンポーネント  | 独自ブロックの実体。記事は props だけ持ち、データは表示時にAPIから取る                |
| テンプレート    | ページの種類ごとの編集制約。コード側に定義する                                        |

## データの持ち方

```
pages   ─┐
news    ─┤
blogs   ─┼─▶ articles（タイトル / 本文 = BlockNoteのブロック配列JSON）
shops   ─┤
artists ─┘
```

- **タイトルと本文はどの種類でも `articles`**。News の個別記事も、模擬店の詳細も、ホームも同じ形
- **タイトル以外で一覧に必要な情報はサマリー側**が持つ。サマリー1行が記事1件を参照する（1対1）
- 記事は単独では表に出ない。必ずどれかのサマリーからぶら下がる

サマリーを分ける理由は3つ。

1. **一覧で本文を読まなくて済む**。20件並べるのに20件分の JSON を転送したくない
2. **並び替え・絞り込み・検索が列でできる**。JSON の中を漁らない
3. **種類ごとに必要な列が違う**。模擬店には「会場・出演時間」、ブログには「抜粋」が要るが、
   本文の形はどちらも同じ

固定ページ（ホーム・お知らせ一覧・スケジュールなど）も同じ構造で、`pages` が
slug・ナビの表示名・テンプレート名・機能のオンオフを持ち、本文は `articles` を参照する。

## 記事の中身

BlockNoteのブロック配列（JSON）をそのまま持つ。ブロックは2種類。

| 種別               | 例                                     | データ                       |
| ------------------ | -------------------------------------- | ---------------------------- |
| テキスト系         | 見出し・段落・リスト・画像・リンク     | **中身そのもの**を記事が持つ |
| 独自コンポーネント | 模擬店一覧・スケジュール表・天気・地図 | **props だけ**を記事が持つ   |

```json
[
    {
        "type": "heading",
        "props": { "level": 2 },
        "content": [{ "type": "text", "text": "今日の模擬店" }]
    },
    {
        "type": "paragraph",
        "content": [{ "type": "text", "text": "現金のみです。" }]
    },
    {
        "type": "shopList",
        "props": { "day": 1, "tags": ["food"], "sort": "popular" }
    }
]
```

BlockNoteのドキュメントは（ProseMirrorのような単一の `doc` ルートではなく）**ブロックの配列**。
独自コンポーネントは、ジェネリックな「componentノード」ではなく **`type` がそのままコンポーネント名になる
専用ブロック**として定義する（例: `shopList`）。リストのネストはブロックの `children` で表現する。

**コンポーネントブロックは実データを持たない。** 持つのは「どれを・どう並べて出すか」だけ。

- 元データを1か所直せば、そのコンポーネントを置いた全ページに反映される
- 記事の保存と、模擬店データの更新がぶつからない
- 同じデータを別ページでも使うとき、キャッシュが効く

## 表示（apps/web）

1. slug から記事とサマリーを取得する
2. 記事JSON（ブロック配列）を上から辿り、ブロックをReact要素に変換する
3. 独自コンポーネントのブロック（`type` がコンポーネント名そのもの）に当たったら、**レジストリ**
   （`type` → React コンポーネント）から実体を引いて props を渡す
4. 各コンポーネントが**自分で必要な分だけ** API を叩く（TanStack Query）

記事APIはデータを埋め込まない。埋め込むと、記事APIがコンポーネントの種類を全部知ることになり、
キャッシュもページ単位でしか効かなくなる。

- **取得の単位はコンポーネント**。ローディングとエラーの境界も同じ単位に置く。
  天気APIが落ちてもページ全体は表示される
- **知らないブロックは無視して描画を続ける**。新しいコンポーネントを含む記事を古いクライアントが
  開いても白画面にしない（前方互換）

## 編集（apps/admin）

BlockNoteのエディタで、同じ記事JSON（ブロック配列）を直接編集する。

- 文章・見出し・画像は普通のリッチテキスト編集
- 独自コンポーネントは**中身を編集できないブロック**として置き、選択すると props を
  サイドパネルのフォーム（React Hook Form + zod）で編集する
- エディタ上の見た目は、ウェブアプリの実物と厳密に一致させない。
  「何が置かれているか」と props が分かれば足りる。実物の確認はプレビューの役割

## テンプレートとロック

ページの種類ごとに**テンプレート**をコード側に定義し、編集できる範囲を決める。

| テンプレートが決めること | 例                                                     |
| ------------------------ | ------------------------------------------------------ |
| 必須のコンポーネント     | お知らせ一覧ページから `newsList` は消せない           |
| 位置の固定               | ヒーローは必ず先頭                                     |
| 編集できる props         | `shopList` の `day` は変えられるが `eventId` は不可    |
| 挿入できるコンポーネント | ブログ本文に `map` は入れられる、`newsList` は入らない |

- **正本はコード**（`packages/schema`）。DBに置かない。ロックは「壊れないための不変条件」なので、
  運用で外せると意味がない。変えたいときはデプロイする
- **UIで止めるだけにしない。** 保存時にAPI側でも同じ検証をかける。
  エディタの制御はリクエストを直接投げれば迂回できる

## バリデーションの正本

`packages/schema` に一度だけ定義し、3か所から import する。

| 定義するもの               | 使う場所                                         |
| -------------------------- | ------------------------------------------------ |
| コンポーネントごとの props | admin（propsフォーム）/ api（保存時）/ web（型） |
| 記事ドキュメント全体の形   | api（保存時）/ web（描画前）                     |
| テンプレート制約の検証関数 | admin（保存前）/ api（保存時）                   |

コンポーネントを1つ足すとは、**このスキーマ・webのレジストリ・adminのブロック定義の3つを
同時に足す**ということ。どれか1つが欠けると、保存できるのに表示できない記事が作れてしまう。

## マルチテナント

1つのサービスで複数の文化祭を扱う。

- 記事・サマリーを含む全テーブルがイベントを指す列を持ち、**RLS で分離**する
- slug はイベント内で一意。イベントをまたいだ一意性は持たせない
- テンプレートはコード側の定義なので**全イベント共通**。イベントごとに違うページ構成を
  持たせたくなったら、テンプレートを増やして選ばせる
