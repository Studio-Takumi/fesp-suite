## 実装メモ

- **サマリーは記事と1つのリソースにした。** `POST /api/posts` が `articles` + `article_histories` + `posts` を
  1トランザクションで作り、`PUT /api/posts/:id` が記事の保存とサマリーの更新を1回で行う
  （理由: サマリーは記事と `id` を共有していて、URL を分けても指すものが同じ。
  `POST /api/articles` → `POST /api/posts` の2発に分けると、間で落ちたときに本文だけの記事が残る）。
  版の残し方・公開状態の決まりは `PUT /api/articles/:id` をそのまま参照する形にして、二重に書いていない

- **`/api/articles` は残した**（理由: サマリーを持たない記事＝`slug` 付きの固定ページ（ホーム・お知らせ一覧など）が
  引き続きある。サマリーを持つ記事の `id` を `/api/posts/:id` 以外から読めなくする理由も無い）

- **一覧は本文を返さない。** サマリーテーブルを分けた理由そのものなので、`content` と `latest_history` を
  除いた形にした（既存の `GET /api/articles` と同じ扱い）

- **並び順を持つ子は、配列でまとめて置き換える `PUT` にした**（商品・下のナビ・記事のタグ）。
  理由: 1件ずつ作り消しすると `sort_order` の詰め直しが毎回要る。渡した順がそのまま並び順になる

- **模擬店の一覧では `products` も返すことにした**（理由: `shopList` の `showProducts` で
  カードの中に商品を出す。模擬店ごとに数件なので、一覧に含めても重くない）

- **スケジュールだけ取得の単位が粗い。** `GET /api/schedules/:day` で、列と項目をまとめて返す
  （理由: 表示を切り替える単位が Day1 / Day2 で、列や項目を別々に引いてもウェブアプリ側で組み直すだけになる）。
  `:day` は `event_days.id`

- **タグは記事に付く。** `article_tags` が記事を指すので、記事オブジェクトに `tags` を足し、
  書き込みは `PUT /api/articles/:id/tags` にした。`posts` / `shops` / `artists` の作成・保存でも
  `tag_ids` で一緒に渡せるようにしてある

- **前提が未定のものは書かなかった**（マップ #61 は座標の持ち方、天気 #62 は取得元の API、
  PV #108・権限 #109・機能のオンオフ #110 は仕様そのものが未定）
