## 実装メモ

- **サマリーは `articles.id` を主キーに共有した**（理由: 主キーがそのまま記事への外部キーを兼ねるので、
  1記事に2つのサマリーがぶら下がる状態が構造上できない。`article_id` + `unique` で同じ保証を作るより列が1本少なく、
  結合も `on shops.id = articles.id` で済む。公開状態は `articles` が持つので、
  「公開中の模擬店だけ」の絞り込みがこの結合だけで書ける）。
  代わりに `id` へ既定値は付けない（既定値があると、渡し忘れたときに記事と無関係な `id` が静かに入る）

- **サマリーに `event_id` を置かなかった**（理由: `articles` が持っていて、共有主キーなら結合で引ける。
  同じ値を2か所に持つとズレる余地ができる）。RLS は `article_histories` と同じく `articles` を引いて判定する

- **サマリーに名前の列を置かなかった**（理由: 名前 = 記事のタイトル。`article_histories.title` が正本で、
  列に持つと同じものを2か所で直せてしまう）

- **タグの中間テーブルを種類ごとに作らず `article_tags` 1本にした**（理由: タグが付く対象はすべて記事で、
  サマリーは記事と同じ `id` を持つ。`news_tags` / `shop_tags` / `artist_tags` の3本は同じ形になる）。
  `tags` にも種別の列は持たせていない（種類をまたいで同じタグを使う）

- **開催日を `event_days` として独立させた**（理由: Day1 / Day2 は模擬店・出演者・スケジュールが揃って参照する。
  スケジュール側に持つと「Day1 が何月何日か」がスケジュールの中にしか無くなる）。
  `events` に開催期間の列を足さずに済むのも兼ねる

- **場所は `places` が正本で、模擬店・出演者が `place_id` で参照する。
  スケジュール表の列（`schedule_columns`）だけは参照しない**（理由: 列は自由に決めたい。
  会場と1対1にすると、列を増やすのに場所を作る必要が出る）。列の数は行の数で決まるので別に持たない

- **逆向きの参照は持たせなかった。** 場所から模擬店を引くときは `place_id` がその場所を指す行を探す。
  出演者とスケジュールの項目も同じで、`schedule_events.artist_id` の片方向だけにした
  （理由: 両方向に持つと、片方だけ更新された状態が作れる）

- **セットリストは `artists.set_list` の jsonb 列にした**（理由: 出演者の詳細で出すだけで、
  他から引く予定がない）。商品（`products`）は食券などで後から使う予定があるのでテーブルに分けた

- **お知らせとブログは `posts` の1テーブルにし、`is_blog` で分けた**（理由: 見せ方が違うだけで持つ情報が同じ。
  差はサムネイルと抜粋の2列だけで、どちらも `NULL` を許せば足りる）。
  テーブル名を `news` にしなかったのは、ブログの行も入るため

- **注意事項は列にせず、記事の本文の注意書き（`callout`）で書く形にした**（理由: #66 で足したブロックで
  同じことが書ける。列にすると同じ内容を2か所で直せてしまう）。
  一方 **紹介文は列**にした（書式なしの文章で、一覧にも詳細にも出るため）

- **`authorities` は `event_members` への複合外部キーにした**（理由: そのイベントに所属していない人に
  権限だけ残る状態を作らない。脱退すると権限も消える）。`can_*` の6つは叩き台で、粒度は #105 の「決めたいこと」に残した

- **`page_views` は書かなかった**（理由: #56 〜 #63 のどれにも属さず、行数の桁が他と違うので、
  粒度（生ログか日次集計か）を決めてから別 Issue で足す）
